Clase: Observabilidad Inteligente y Auto-Remediación en Kubernetes con Kagent

Objetivo de la Clase

En esta sesión práctica, aprenderemos a monitorizar aplicaciones desplegadas en Kubernetes (k8s) y automatizar la respuesta ante incidentes utilizando Kagent, un framework nativo de Kubernetes para agentes de IA. Integraremos Prometheus y Grafana con la API de Kubernetes y utilizaremos servidores MCP (Model Context Protocol) para permitir que un agente de IA diagnostique y solucione fallas del clúster de forma autónoma.

¿Qué es Kagent? Kagent es un framework que ejecuta agentes de IA como cargas de trabajo nativas de Kubernetes. Utiliza CRDs (Custom Resource Definitions) como ModelConfig y Agent para conectar LLMs con servidores MCP que les otorgan herramientas para interactuar con el clúster.

Paso 1: Despliegue de la Aplicación en Kubernetes

Nuestra aplicación LTI ya cuenta con sus manifiestos base en la carpeta k8s/ (base de datos, backend y frontend). Procederemos a aplicarlos en el clúster.

# Aplicar los manifiestos de la base de datos y la aplicación LTI
kubectl apply -f k8s/db.yaml
kubectl apply -f k8s/backend.yaml
kubectl apply -f k8s/frontend.yaml

Para comprobar que todo está ejecutándose correctamente:

kubectl get pods,svc

Paso 2: Instalación de la Suite de Observabilidad en Kubernetes

Desplegaremos Prometheus y Grafana dentro de nuestro clúster de Kubernetes para recoger las métricas del backend del LTI.

2.1. Crear el manifiesto de Observabilidad: k8s/observability.yaml

apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-config
  namespace: default
data:
  prometheus.yml: |
    global:
      scrape_interval: 15s
    rule_files:
      - /etc/prometheus/alert.rules.yml
    scrape_configs:
      - job_name: 'lti-backend'
        static_configs:
          - targets: ['backend:8080']
  alert.rules.yml: |
    groups:
      - name: lti-alerts
        rules:
          - alert: HighLatencyP99
            expr: http_request_duration_seconds{quantile="0.99"} > 0.5
            for: 1m
            labels:
              severity: critical
            annotations:
              summary: "Alta latencia detectada en el Backend"
              description: "La latencia del percentil 99 (P99) ha superado los 500ms durante más de 1 minuto."
          - alert: HighErrorRate
            expr: rate(http_requests_total{status=~"5.."}[1m]) / rate(http_requests_total[1m]) * 100 > 5
            for: 30s
            labels:
              severity: warning
            annotations:
              summary: "Tasa de errores 5xx elevada"
              description: "Más del 5% de las solicitudes HTTP en el último minuto han devuelto errores 500."
---

Paso 3: Configuración de Kagent y ModelConfig

Para dotar de inteligencia a nuestro clúster, utilizaremos Kagent conectado a un LLM local (Ollama) o remoto (OpenAI/Gemini).

3.1. Verificar o Crear el ModelConfig: k8s/kagent-ollama.yaml

apiVersion: kagent.dev/v1alpha2
kind: ModelConfig
metadata:
  name: default-model-config
  namespace: default
spec:
  provider: Ollama
  model: gemma4:e2b
  ollama:
    host: http://host.docker.internal:11434
Nota: Si deseas utilizar OpenAI, puedes configurar un `ModelConfig` que apunte al proveedor de OpenAI referenciando un secreto con la API Key correspondiente.

Paso 4: Definición del Agente SRE con Servidores MCP

Un agente inteligente necesita herramientas para actuar. A través del protocolo MCP (Model Context Protocol), vincularemos herramientas de Kubernetes y Prometheus al agente para que pueda inspeccionar y resolver problemas de forma autónoma.

4.1. Crear el manifiesto del Agente SRE: k8s/agent-sre.yaml

apiVersion: kagent.dev/v1alpha2
kind: Agent
metadata:
  name: sre-agent
  namespace: default
spec:
  type: Declarative
  description: "Virtual SRE Agent for LTI application auto-remediation"
  declarative:
    modelConfig: default-model-config
    systemMessage: |
      Eres un ingeniero de SRE virtual autónomo dentro del clúster de Kubernetes. 
      Tu objetivo es diagnosticar y mitigar incidentes de producción de la aplicación LTI.
      Tienes acceso al servidor MCP 'kagent-tool-server' para realizar tareas de soporte e infraestructura.
      
      Cuando se detecte una alerta, investiga la causa raíz utilizando las herramientas disponibles:
      - Lista y describe los pods, deployments y servicios.
      - Obtén logs de los contenedores afectados.
      - Si la falla es por una nueva versión defectuosa, ejecuta un rollback.
      - Si la falla es por saturación de carga, escala el deployment correspondiente.
      
      Reporta detalladamente en español tus hallazgos, tu razonamiento y las acciones tomadas.
    tools:
    - mcpServer:
        apiGroup: kagent.dev
        kind: RemoteMCPServer
        name: kagent-tool-server
        toolNames:
        - k8s_get_resources
        - k8s_get_pod_logs
        - k8s_apply_manifest
        - k8s_patch_resource
        - k8s_describe_resource
        - k8s_delete_resource
      type: McpServer

# Aplicar el Agente en el clúster
kubectl apply -f k8s/agent-sre.yaml

Paso 5: Automatización de la Remediación ante Eventos (Khooks)

Para hacer reactivo al agente sin necesidad de configurar complejos webhooks en Alertmanager, utilizamos Khook, el controlador de Kubernetes para agentes reactivos de Kagent. Khook escucha eventos específicos del clúster (como reinicios de pods, fallos de OOM, o caídas de red) y activa el agente SRE correspondiente.

5.1. Crear el manifiesto del Hook: k8s/remediation-hook.yaml

apiVersion: kagent.dev/v1alpha2
kind: Hook
metadata:
  name: sre-remediation-hook
  namespace: default
spec:
  eventConfigurations:
    - eventType: pod-restart
      agentId: sre-agent
      prompt: |
        Se ha detectado un reinicio en el pod '{{.ResourceName}}' en el namespace '{{.Namespace}}'. 
        Por favor, actúa como el SRE de guardia, investiga las causas de la falla leyendo los logs y la descripción del pod mediante tu servidor MCP de herramientas, y aplica una acción correctiva si procede. 
        Reporta tus hallazgos.

# Aplicar el Hook en el clúster
kubectl apply -f k8s/remediation-hook.yaml
Ventajas de Khook:
  • Deduplicación & Debouncing: Evita saturar al LLM con alertas repetidas si un contenedor entra en CrashLoopBackOff.
  • Nativo de Kubernetes: Usa el modelo de recursos declarativo de KRM en vez de servidores de mensajería externos.
  • Control de Concurrencia: Asegura que solo se ejecute una instancia del agente a la vez para resolver el problema.

Paso 6: Escenarios Comunes de Auto-Remediación en Kubernetes

A continuación se detallan las respuestas automáticas que realiza el agente utilizando las herramientas de su servidor MCP de Kubernetes:

Alerta Detectada Causa Raíz Acción de Kagent vía MCP Acción Equivalente en CLI
High Error Rate Bug introducido en nueva release. Rollback automático al deployment previo. kubectl rollout undo deployment/backend
DDoS Attack Tráfico anómalo de una IP atacante. Aplicar NetworkPolicy para aislar/bloquear la IP. kubectl apply -f network-policy-block.yaml
Disco Lleno (Disk Full) Acumulación de archivos de log efímeros. Reiniciar pods para liberar el almacenamiento efímero. kubectl rollout restart deployment/backend
OOM Killed Límite de memoria superado en el pod. Ajustar los resource limits en el Deployment. Modificación de spec.resources del Deployment.
Dependency Down API externa inaccesible. Activar Circuit Breaker a nivel de ConfigMap. Modificar ConfigMap para activar bypass offline.
DB Connection Pool Saturación de conexiones en la base de datos. Escalar el número de pods para distribuir carga. kubectl scale deployment/backend --replicas=3

Paso 7: Guía de Simulación de Errores e Incidentes

Para probar al agente SRE de forma práctica, hemos preparado un script en la raíz del proyecto llamado simular_errores.sh. Este script automatiza la inyección y recuperación de fallas en el clúster:

7.1. Simular un fallo de memoria (OOM) en el Backend

Esto forzará al pod de backend a entrar en CrashLoopBackOff por falta de RAM:

./simular_errores.sh oom

7.2. Simular un fallo de descarga de imagen (ImagePullBackOff) en el Frontend

Esto modificará el manifest para usar una tag de imagen inexistente:

./simular_errores.sh image

7.3. Simular caída total de réplicas en el Backend

Esto escalará a 0 réplicas el deployment de backend para verificar la indisponibilidad de servicio:

./simular_errores.sh scale

7.4. Restaurar el clúster a su estado saludable

Para limpiar y reestablecer todo una vez realizadas las pruebas:

./simular_errores.sh restore

Paso 8: Integración y Automatización con n8n

En este paso, utilizaremos n8n como la plataforma de orquestación para coordinar las alertas generadas por Prometheus, enriquecerlas mediante inteligencia artificial (LLM) y disparar remediaciones automatizadas en Kubernetes utilizando Kagent y su agente de SRE.

8.1. Ejercicio 1: Flujo de Diagnóstico Automatizado (Alerta -> LLM -> Slack)

El objetivo de este flujo es recibir la alerta técnica de Prometheus, consultar el estado del pod afectado de forma automática, pasárselo a un LLM para diagnosticar el problema y publicar un informe en Slack con un botón para mitigar el error.

Configuración del Flujo en n8n:

  1. Webhook Node: Expone un endpoint HTTP que recibe los JSONs de alerta de Prometheus Alertmanager (ej. fallo por OOM en el backend).
  2. HTTP Request Node (Kubernetes API): Consulta al pod afectado haciendo una petición GET a la API del clúster (o utilizando las herramientas del MCP server) para extraer los últimos 50 logs y el JSON de descripción del pod.
  3. Basic LLM Chain / AI Agent Node: Pasa la información recopilada (alerta, logs y descripción) a un nodo de modelo de lenguaje (como OpenAI u Ollama local). El System Message del LLM le indica actuar como un experto en diagnóstico y estructurar su análisis con:
    • Diagnóstico: Qué ha fallado.
    • Causa Raíz: Por qué ha fallado.
    • Recomendación: Qué acciones de mitigación se sugieren.
  4. Slack Node: Publica en el canal de alertas de Slack el reporte estructurado en español, agregando un botón interactivo llamado "Ejecutar Auto-Remediación con SRE Agent" que envía el evento a un segundo Webhook.

8.2. Ejercicio 2: Flujo de Remediación con SRE Agent (Acción Slack -> Kagent -> Slack Update)

El objetivo de este segundo flujo es procesar el clic del usuario en Slack, disparar el SRE Agent de Kagent en el clúster de Kubernetes, capturar la acción realizada por el agente de IA, y actualizar el mensaje en Slack para reportar la solución.

Configuración del Flujo en n8n:

  1. Webhook Node: Escucha los payloads interactivos de Slack activados al pulsar el botón "Ejecutar Auto-Remediación con SRE Agent".
  2. HTTP Request Node (Kagent Run): Realiza una petición POST al endpoint de Kagent Controller (ej. http://kagent-controller:8083/v1alpha2/namespaces/default/agents/sre-agent/run) indicándole al agente SRE que ejecute el runbook para resolver el incidente actual.
  3. HTTP Request Node (Fetch Execution Trace): Consulta el resultado de la ejecución del agente (polling o callback) para recuperar qué herramientas utilizó (ej. k8s_patch_resource para escalar) y la descripción de la mitigación aplicada.
  4. Slack Node (Update): Actualiza el mensaje original del canal de alertas de Slack cambiando su estado a "Resuelto (Auto-Remediado)", aplicando un color verde y detallando la acción de mitigación aplicada por el Agente SRE (ej. "Escaladas las réplicas del Backend a 3 pods").
